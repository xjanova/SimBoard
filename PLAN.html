ข้อ 1 · SPICE ไม่ใช่ของที่เขียนเอง

เอนจิน SPICE ที่ใช้ได้จริงคือสามสิบปีของงานวิจัย ไม่ใช่โมดูลหนึ่งในแผน โมเดล MOSFET ตัวเดียว (BSIM4) เกินสองหมื่นบรรทัด C และส่วนที่ยากที่สุดไม่ใช่สมการ แต่คือ heuristic ตอนไม่ลู่เข้า — gmin stepping, source stepping, การเลือก timestep จาก local truncation error สร้างเองแล้ว "รันได้" ใน 3 เดือน แต่จะเจอวงจรที่ไม่ลู่เข้าไปตลอดอายุโปรดักต์ และช่างมืออาชีพจะเลิกใช้ทันทีที่เจอครั้งแรก

  • ใช้ ngspice — ทายาทตรงของ SPICE3f5 ที่สเปกระบุไว้บน title bar อยู่แล้ว มี API สำหรับฝังในโปรแกรม GUI โดยเฉพาะ (ngSpice_Init / ngSpice_Circ / ngGet_Vec_Info) และ KiCad ก็ใช้ตัวนี้
  • รันเป็นโปรเซสแยก ไม่ใช่ลิงก์เข้าไปในแอป — ได้สามอย่างพร้อมกัน: วงจรที่ทำให้ solver ค้างไม่ทำให้งานที่ยังไม่เซฟหาย, กด Stop ได้จริงเพราะฆ่าโปรเซสได้, และเป็นกำแพง license ที่สะอาดถ้าจะขายแบบปิดซอร์ส
  • ค่าใช้จ่ายของกำแพงนี้ต่ำมาก — หนึ่งรัน = ส่ง netlist เข้าไปครั้งเดียว รับ rawfile กลับมาก้อนเดียว ไม่ใช่การคุยกันทุกเฟรม ต่างจากการขนข้อมูลเข้า JS ซึ่งเกิดทุกครั้งที่รีเฟรชกราฟ
  • ต้องตรวจ license ก่อนขาย — ngspice รวมโค้ดหลาย license เข้าด้วยกัน (แกน BSD จาก Berkeley + ส่วนที่ contribute มาทีหลัง) ให้ฝ่ายกฎหมายอ่านก่อนปิดกล่อง ส่วน Xyce ที่สเปกเขียนคู่ไว้เป็น GPLv3 — ใช้ผ่านโปรเซสแยกเท่านั้น อย่าลิงก์เด็ดขาด
ข้อ 2 · "AI จัดวาง + เดินลาย" ไม่ใช่งานของ LLM

ที่หน้าจอ 8 เขียนว่า AI — ของจริงคือ combinatorial optimization และนั่นเป็นข่าวดี เพราะมันทำให้ผลลัพธ์ทำซ้ำได้ อธิบายได้ และไม่ต้องต่อเน็ต ที่สำคัญคือ ช่องติ๊กห้าช่องในม็อกอัพนั่นแหละคือ cost function อยู่แล้ว:

  • ลายสั้นที่สุด → ผลรวมความยาว ratsnest แบบ half-perimeter
  • กระจายความร้อน → penalty เมื่อชิ้นที่กินกำลังสูงอยู่ใกล้กัน + bonus เมื่อชิดขอบบอร์ด
  • เว้นระยะไฟแรงสูง 2.0 mm → hard constraint ไม่ใช่ cost — ละเมิดแล้ว reject ทันที
  • จัดกลุ่มตามบล็อกวงจร → penalty ตามระยะระหว่างชิ้นที่ติดป้ายบล็อกเดียวกัน
  • ลดจำนวนเวีย → cost ต่อ via ในขั้นเดินลาย

วางชิ้นด้วย simulated annealing (หรือ force-directed ตามด้วย local search) เดินลายด้วย A* บนกริดพร้อม rip-up-and-retry ถ้าอยากลัดทาง มี freerouting (Java, GPLv3) ให้เรียกเป็น sidecar ได้ — แต่ GPLv3 อีกเช่นกัน ต้องแยกโปรเซส

ที่ LLM ช่วยได้จริงมีจุดเดียว คือ อ่าน netlist แล้วเดาว่าอะไรเป็นบล็อกอะไร ("กลุ่มนี้คือภาคจ่ายไฟ", "ตัวนี้คือ decoupling ของ U2") เพื่อป้อนข้อ 4 ให้อัตโนมัติ — เป็นฟีเจอร์เสริมชั้นบน ไม่ใช่ตัวจัดวาง และต้องทำงานได้แม้ปิดเน็ต

เฟส 0 · เริ่มพรุ่งนี้ได้เลย

สามสไปก์ สามสัปดาห์ แต่ละอันมีเกณฑ์ผ่านที่วัดได้ ไม่ใช่ "ลองดูก่อน" ถ้าอันไหนไม่ผ่าน แปลว่า stack ผิด — และรู้ตอนสัปดาห์ที่ 3 ถูกกว่ารู้ตอนเดือนที่ 8 มาก

  1. S1
    ngspice sidecar จาก C#

    รัน ngspice.exe เป็นโปรเซสลูก ป้อนเนตลิสต์ 555 astable ตัวเดียวกับในม็อกอัพ อ่าน rawfile กลับมา แล้ววาดรูปคลื่นที่ตรงกับ CH1/CH2 ในหน้าจอ 5

    ผ่านเมื่อ · รัน transient 0–20 ms กลับมาใน < 2 วินาที · กด Stop กลางคันแล้วโปรเซสตายจริงไม่มีซาก · ค่า Vpp/ความถี่ตรงกับ 4.98 V / 1.442 kHz ที่สเปกระบุ
  2. S2
    Skia canvas ที่หนักจริง

    วาดวัตถุ 10,000 ชิ้น (สัญลักษณ์ + สาย + ป้าย) บน Avalonia custom draw op พร้อม pan/zoom และ hit-test ด้วย R-tree

    ผ่านเมื่อ · แพนต่อเนื่องคงที่ 60 fps ที่ 10,000 ชิ้น · hit-test ตอบใน < 1 ms · หน่วยความจำนิ่งหลังแพนสองนาที ไม่ไต่ขึ้น
  3. S3
    โครม Aqua 3D · Liquid ของจริง + ไทย 10px

    ทำ TitleBar · Button · ช่องจม · ListView เป็น ControlTemplate จริง ขับด้วย token dictionary แล้วเทียบกับ theme-aqua-3d-liquid.png ทีละพิกเซล พร้อมใส่ป้ายไทยที่ยาวที่สุดในสเปกลงไปทุกช่อง

    ธีมเริ่มต้นของโปรดักต์คือ Aqua (เปลี่ยนจาก Windows ME) — และนี่เป็นข่าวดีสำหรับสไปก์ เพราะ Aqua คือธีมที่ยากที่สุดในเจ็ดตัว: --face เป็นเกรเดียนต์ ไม่ใช่สีตัน · --raiseSh ซ้อน inset shadow สี่ชั้น · caption เป็นเกรเดียนต์ห้าสต็อป · --rad 9px · ปุ่มหน้าต่างเป็น radial-gradient ส่วน ME เป็นสีตันกับขอบ 1px ล้วน ถ้าระบบ token เรนเดอร์ Aqua ได้ ที่เหลืออีกหกธีมคือของง่าย — พิสูจน์เคสยากก่อนคือการลดความเสี่ยงที่ถูกต้อง

    ผ่านเมื่อ · สลับ Aqua ↔ ME ด้วยการเปลี่ยน dictionary ชุดเดียว ไม่แตะโค้ดคอนโทรล (สองตัวนี้อยู่คนละสุดขั้ว เจลกับขอบตัน — ผ่านคู่นี้ได้แปลว่าผ่านหมด) · ภาพต่างจากม็อกอัพน้อยกว่า 2% · ป้ายไทยที่ยาวที่สุดไม่ล้นช่อง 76px · วรรณยุกต์ไม่ซ้อนสระที่ 10px
